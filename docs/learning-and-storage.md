# Video formats and local SQLite storage

Introduced in v0.1.0-beta.2. It uses Node's built-in SQLite:
Node 22.16+ on the 22.x line or Node 24+ (Node 24 recommended). Node 23 is unsupported
because its built-in SQLite has no FTS5 full-text search, which memories use; the launchers
probe for FTS5 before starting. No database server, package installer or hosted service is
required.

## Where things live

New studios default to local application data: `~/Library/Application Support/Video Octopus/Studio`
on macOS, `%LOCALAPPDATA%/Video Octopus/Studio` on Windows, and
`$XDG_DATA_HOME/video-octopus/studio` (normally `~/.local/share/...`) on Linux.
Users can choose another location. Existing studios stay in place.

`<studio>/.studio/studio.sqlite` is authoritative for:

- Reviewed scoped memories, revisions, app-owned searchable history and forget exclusions. See [Memories](memories.md).
- Skill content, content hashes, ownership/selection and retained skill versions.
- Creator profiles, their versioned brands and format definitions.
- Resources (photos, logos, shapes, reference thumbnails, fonts, style notes) at All channels, a channel or one
  video, including brand assets; their bytes live in the file store. See "Packaging and resources" below.
- Packaging records: thumbnail cards, contact sheets, winners, the main thumbnail and the working title.
- Shared instruction documents and supported preferences, including retained versions.
- Brand research sessions, evidence and reviewed approvals.
- Learning sessions (format conversations), references, review revisions, approvals and the
  creator's own chat messages in them (the provenance for instruction evidence).
- Approved rules, learnings, workflow skill content (`SKILL.md`, `guide.md`) and version history.
- Records of every skill file (assets, knowledge, key frames): name, note, kind, tags, size, type,
  sha256, source and the versions that use it. Their bytes live in the file store (below).
- Project pins for brand, instructions, selected skill snapshots and learned formats, plus scene-plan approval tokens.
  A token is the hash of the scene plan (without its top-level `approved` and the scenes' build `status`), the locked
  cut and the pinned version (`server/studio.mjs` `planToken`). **Approve plan** in the editor's Plan stage records it
  together with the plan's own `approved` (one decision; the Script & learned format panel's approval does both too),
  and Ask for changes removes both. When the plan or the cut changes after approval, Approve the plan is the next step
  again and Build waits. Tokens made before this rule (the plan's raw bytes) are still accepted while the bytes match.

Skill file bytes live in a content-addressed file store in the studio:
`<studio>/.studio/files/<first 2 hex>/<sha256><.ext>`. Identical files are stored once, writes
are temp + fsync + rename, and the store never follows symbolic links. Skill folders hold
copy-on-write clones of these files (no extra space on APFS; a normal copy elsewhere), never
links. See "Skill files: assets and knowledge" below.

Video/audio, intake originals, extracted frames and editor working documents remain
ordinary files. Existing project/timeline JSON interfaces and technical application
settings are not wholesale converted into database blobs in this change.
The app manages their locations; users do not need to organize skill folders.

Agent tools still require files. `.claude/skills/`, `skills/custom/`,
`skills/overrides/`, approved learning-package folders and the generated format skills
(`.claude/skills/format-<8 characters of the format id>/`) are projections/working
copies. SQLite retains their accepted content. Do not treat generated JSON manager
state as authoritative. Missing skill publications regenerate on startup; changed
working files require explicit **Refresh / import file edits** or **Rebuild agent files**.
Rebuild retains displaced files in the publication backup. Explicit import can also
record intentional deletions/disabled choices; review them in the Skills screen.

## Skills and app updates

**Core**, **Customized core**, **Personal** and **Format** distinguish ownership in Skills.
Read/edit a core skill to create a saved customized version. Personal skills can
be created in the app or imported through the existing GitHub installer. A **Format**
skill is generated by the app, one per Video format (see [Format skills](#format-skills-and-continuing-conversations)):
it cannot be edited, disabled or customized in Skills, and is changed only by saving a
new format version. Earlier releases published each approved version as a personal
`learned-<version id>` skill; existing ones are left untouched, and no new ones are created.
Each skill card has a short explanation stored in its SQLite snapshot. Read/edit lets you change the explanation separately from the workflow: explanation-only edits retain Core ownership. Personal explanations survive sync and restore with skill history. Existing skills receive a local summary without model calls.

Core updates retain personal content and the existing API compatibility gates.
All three agent adapters use a checked publication. New projects receive selected
skills from their pinned snapshot; unscoped chats use the active studio publication.

First migration applies the existing conservative ownership rules to legacy files,
then atomically records accepted state and deduplicated content in SQLite.
The filesystem journal backs up displaced roots. SQLite is the commit point:
interruption before its transaction commits rolls publication back; interruption
afterwards completes bookkeeping. Skill history can restore a database snapshot;
restored choices remain held until the creator resumes updates. Power-loss testing
and large-library performance remain unverified.

No updater automatically merges Markdown. An external edit cannot silently replace
canonical content during startup. A missing/corrupt database is not reconstructed
from generated state once the studio has migrated; use a database backup.

## Studying examples

1. Choose a format in Video formats. The page is a list and a detail: the left
   list shows every profile (channel, brand or series) with its formats, and the
   right side shows the selected format with **New video**, its Setup, Style guide
   and Skills, and its studies. **+ New format** in the header (or **+** beside a
   profile) adds a format; the dialog has a Profile field. Profiles are shared with
   Brand settings and New video. Each profile's formats learn separately, even if
   two channels both have a format called Shorts. Copying an approved format, Start
   with an idea or script, Edit brand and Back up local database are under
   **More options**.
2. Click **Study examples**. The study has three numbered steps, with the
   assistant chat beside them. **Add examples:** paste links (pasting complete
   URLs adds them straight away; Enter or Add links also works), choose or drop
   files, or add a written note. Suggestions the assistant saves appear in this
   step automatically. **Start the study:** guidance and depth are optional;
   Start study is available as soon as there is an added or pasted example and
   registers any still-pasted links first. **Review and approve** appears once the
   agent has written a proposal. New sessions automatically discover supported
   patterns across scripting, pacing, visuals, captions, sound and knowledge;
   earlier sessions keep their chosen scope. The study name and frame-extraction
   tools are under Advanced. Settings save when adding examples, starting, chatting
   or renaming. Uploads are copied, limited to 512 MB each and 20 references per
   session; original files are untouched. Successful batch items remain if a later
   item fails.
3. Optionally extract local video frames. Overview samples up to about 30 frames
   per video. Detailed extraction uses up to four frames/second, at most five
   minutes per video and 2,400 frames per session. Coverage receipts identify
   unexamined spans; resumptions reuse completed references. Nothing downloads or
   selects a model. Links and transcription are handled by the chosen agent/tools.
4. Click **Start study** with the configured Claude Code, Codex or Pi adapter. A separate
   chat uses manual permissions and a session working directory. References are
   evidence, not instructions. This is **not an OS filesystem sandbox**: permissions
   and review still matter. The agent must report inaccessible sources and gaps;
   images alone cannot establish timing or sound. This discovers patterns in
   supplied references, not an automatic search for reference videos. Provider
   access and study quality need real-user testing.
5. Review `work/proposal.json`: each rule needs a stable ID, selected focus area,
   confidence and evidence: an observation citing an actual session reference, a
   quoted creator message from this conversation, or the creator's direct edit.
   Each draft rule is shown as **New** or **Changed** (with the previous text); rules
   listed under `remove` are shown as **Removed**. Keep, edit or discard each change.
   Review the workflow, learnings and linked reusable assets too. This checks
   structure and source identity, not the truth of the model's conclusions.
6. Approval saves a new immutable format version and makes it active. Stale proposals,
   session revisions or competing active-version changes are rejected; when another
   conversation or History moved the active version, the draft must be rebased first.
   Unrelated rules survive; discarded replacements preserve their prior rule; a
   discarded removal keeps the rule. Assets are a reviewed replacement collection, or
   inherited when empty. The workflow is inherited when the draft omits it. The
   conversation stays open (see below).
7. Start a project with an idea, script or footage/narration. The project pins the
   exact approved version. New approvals and format rollback do not change it.
   Use the existing script editor, prompter and recorder. A project upgrade shows
   the old/new rules and requires a deliberate save.
8. For learned projects, the step rail requires a locked cut before planning/building
   and explicit approval of the current scene plan before Build. Changing the plan,
   cut or learned version invalidates that approval. Full-build preference still
   preserves checkpoints. Free-form agent chat is governed by its instructions and
   permissions; these UI gates are not an agent execution sandbox.
9. Use **Learn from this project** for a structured recap and another reviewed
   learning version. No weekly schedule is enabled.

## Format skills and continuing conversations

UI words: **channel** is a profile, a **conversation** is a learning session and a
format's **skill** is its approved guide. Internal IDs, tables and routes keep their names.

- **Conversations continue after approval.** Saving records the version in the session's
  `approvedVersions`, moves its `baseVersion` to the new version, archives the used draft
  as `work/proposals/<version id>.json` and reopens the conversation. Sessions approved by
  an earlier release reopen the same way (on the format's current version) when the
  creator next chats, configures or adds to them. References cited by any saved version
  cannot be removed from their conversation.
- **Instruction evidence.** Every creator message in a format conversation is stored in
  SQLite (`learning_messages`) with the same original message ID the memory feature uses,
  and the agent sees that ID beside the message. A rule, removal or learning may cite
  `{"kind":"instruction","messageId":"…","quote":"…"}`; the ID must belong to this
  conversation's stored creator messages (messages captured earlier by the memory feature
  also count, unless forgotten) and the quote must appear in that message. App-written
  briefs never count. Plain-language requests ("use blue instead of red") therefore make a
  valid draft without new examples.
- **Direct edits.** The pencil (`POST /api/learning/formats/:id/draft-rule`) writes the
  creator's rule text, or a removal, into the format's open conversation draft (creating a
  conversation if none is open) with `{"kind":"manual","note":"Edited by creator"}`
  evidence that is checked against the stored edit. It is still reviewed and saved.
- **Learnings (shown as Insights).** A draft may include `learnings: [{text, evidence}]`: observations, not
  rules. They accumulate in each version package.
- **Key frames.** On approval, up to six evenly spaced extraction frames per studied
  video reference are stored with the version (in the file store, recorded by hash). The
  original video stays in the conversation's intake folder.
- **One generated skill per format.** `.claude/skills/format-<8 characters of the format
  id>/` holds the ACTIVE version: `SKILL.md` (when to use it, rules summary, workflow,
  pointers), `rules.md`, `examples/` (`examples.md` with each studied reference's name,
  link or original path, notes and version, plus key frames), `assets/`, `knowledge/`
  (with an index in `SKILL.md`), `learnings.md` and `videos.md` (projects pinned to each version). The name never changes on rename; the
  description is regenerated from the current channel and format names. It is rebuilt from
  SQLite on approve, activate, rename, archive and every skill sync, including startup.
  It is a distinct generated kind: never written into `skills/custom/`, never imported from
  edited copies, and a personal skill using the same name is withheld with a notice while
  its files are kept. An edited copy no longer blocks chats: the next chat (or startup)
  moves the edited folder to `.studio/edited-skill-files/<time>-format-…`, puts the saved
  version back from SQLite and says so once in that chat; other skills are untouched.
  When the rebuild must wait for running work, the save still succeeds and reports a
  warning; the rebuild runs as soon as nothing is working (checked twice a second while
  one is pending), and at startup. The format skill view reports `pending` meanwhile.
- **New videos.** Projects still pin the version (and the studio-wide format skill is not
  part of their skill snapshot). Each project's generated context gets its own copy of
  the pinned version's format skill at
  `<project>/.octopus/context/.claude/skills/format-…/`, named with the names pinned at
  creation. Claude Code receives that context folder with `--add-dir` (it loads
  `.claude/skills` from it); Codex receives the skill folder as an extra skill root and pi
  as `--skill`. The project context states the pinned version and, when the format has a
  newer active version, that it does not apply. Pinned projects created before this change
  receive the new `.claude/skills` context folder on their next materialization; the old
  `.octopus/context/skills` folder is left in place, unused.
- **Rename, setup and archive.** Channels can be renamed and archived; formats can be
  renamed, change type or target length (future videos only) and be archived. Archive
  hides them from New video and withdraws the format skill; nothing is deleted, existing
  projects and versions are untouched, and they can be restored. Each change checks the
  record's `revision`.

## Skill files: assets and knowledge

A format's skill can hold real files, up to **300 per skill** (assets and knowledge together)
and **1 GB per file** (`MAX_SKILL_FILES`, `MAX_SKILL_FILE_BYTES` in `server/file-store.mjs`).

- **Assets** are files a video uses directly: backgrounds, icons, logos, PNGs, motion-graphics
  files, styles, fonts. They are projected to `assets/<name>`.
- **Knowledge** is reference material the agent reads when a video needs the facts: product
  sheets, specs, brand facts, price lists (Markdown, text, CSV, JSON, PDF or images). They are
  projected to `knowledge/<name>`, and `SKILL.md` keeps only an index (title, one line, path) so
  the agent opens a file when it is relevant.
- **Adding files.** Format home → **Files** (Assets · Knowledge) → **Add files**, or **Add to
  skill** in the conversation composer. Uploads stream into the open conversation's draft
  (`work/assets/` or `work/knowledge/`), exactly like a direct rule edit; **Remove** stages a
  removal. The Files tab and the draft dock show New / Changed / Removed markers; the review
  asks for a keep/discard decision per file; saving creates the next version. An agent can do
  the same from a conversation: `"assets":[{file, note}]`, `"knowledge":[{file, title, note}]`
  and `"removeFiles":["assets/old.png"]` in `work/proposal.json`. Saved files carry forward;
  re-listing an unchanged file is not a change. Each row shows name, note, kind, size, the
  version that added it and **Show in Finder**.
- **Versions and pins.** A version records each file by hash. Pinned project copies resolve the
  same hashes, so a project pinned to v1 keeps v1's files exactly. Version folders under
  `.studio/learning/versions/` now hold only `guide.md`, `SKILL.md` and `package.json`; older
  versions keep the copies they already have (still verified).
- **Projections.** The published format skill's file list is `.octopus-files.json`. The skill
  snapshot in SQLite leaves those files out (so their bytes never enter the database); after
  every skill sync they are cloned in from the store. A projected file that no longer matches
  its hash is restored, and the edited copy is kept in `.studio/edited-skill-files/`. Edited
  files in a project's pinned copy block it until Restore project context files, as before.
- **Never deleted automatically.** Storage lists **unused files** (no saved version uses them,
  for example after a failed save) with their total size. **Delete unused files** is explicit
  and refuses the whole request if any listed file is still used.

**Migration.** Studios saved before this change kept asset and key-frame bytes in SQLite
(`learning_blobs`). On first open the app backs up the database to
`.studio/file-store-migration-backups/<id>/studio.sqlite`, writes each blob to the file store
and verifies its hash, and only after every file is verified removes those blob rows (then
compacts the database when it can). `SKILL.md` and `guide.md` stay in SQLite. The migration is
recorded in `file_store_meta`, is safe to run again and resumes after a crash without a second
backup. A blob whose bytes do not match its hash is left in SQLite and reported. Until a file
has moved, the app reads it from SQLite and moves it on use.

One active package per profile/format is supported. Named sibling style variants,
weekly rollups, timed overlays and After Effects export remain later work.
Faceless workflows use imported/recorded narration; no TTS provider is selected.

## Packaging and resources

**Packaging** is an optional first stage of every format (`package` step, kind `app`, action `open-packaging`;
done when a main thumbnail is chosen, or skipped). Nothing waits on it. The project's **Packaging** tab is a chat
with Codex (chat id `<project>.packaging`, always Codex whatever agent runs the project chat, in the project
folder, read-only sandbox, with the project chat's pinned context and memories) plus a board:

- **Generate** asks for one image with six numbered 16:9 ideas in a 3 × 2 grid (one generation). Codex's
  `imageGeneration` item's `savedPath` is copied into the file store at once and the sheet is cut into six cards by
  the known grid (FFmpeg). Resources marked "Use in every thumbnail" that may be sent (see below) go along as
  `localImage` inputs; "More like this" adds up to two cards.
- **Refine** sends one card and makes one 1280 × 720 thumbnail (FFmpeg fills the size), a child card.
- **Board:** star (shortlist), winners (up to 3), one main thumbnail among them, reject, upload old thumbnails.
- **Working title** fills the Post tab's YouTube title only when it is empty, never overwriting; without a post
  kit yet it waits in `packaging/PACKAGING.md`.
- A Codex usage limit (`usageLimitExceeded`) marks the sheet failed with the reset time.
- **Use this idea** (a card's ⋯ menu, the main card and the main winner slot; `POST /api/packaging/<id>/items/<card>/use`)
  writes an outline stub into the project's `script.md` (the record panel's script): the working title, the brief
  typed next to Generate (`item.brief`), Codex's line for the card (`item.idea = { words, text, hook?, beats? }`,
  older cards fall back to their name) and the hook and three beats when the card has them, labels as `[cues]`
  (server/idea-script.mjs). A script with text is never overwritten: the answer is `{ exists: true }` and the page
  asks, then sends `append: true` (the outline goes under it) or skips. The project chat then offers **Ask Claude to
  outline it**, which only sends a message. An empty board's big action is **Generate 6 ideas** with the brief.
- Needs Codex signed in with a ChatGPT plan; no API key or other provider is used.

SQLite tables: `packaging_projects` (title, main), `packaging_sheets`, `packaging_items`. The project folder gets
projections the agents read: `packaging/PACKAGING.md`, `packaging/packaging.json`, `packaging/thumbnails/` (main,
winners, starred) and `packaging/RESOURCES.md` with `packaging/resources/<level>/` copies.

**Resources** (`resources(id, scope, data)`) store one scope string from the shared ladder
(`server/scope-chain.mjs`): `global`, `profile:<id>` or `project:<id>`. A video sees All channels, its own channel
and itself, never another channel's or video's. Levels are data: the Format level exists in the ladder but is
off for resources; switched on later it needs no table change, and a record at a level that is off shows under the
nearest broader one. Resources stay live (not pinned): the projections are rewritten when the Packaging tab opens
and before each Packaging message. A photo must say **who is in it** (me, someone who agreed, someone else, no
people); "someone else" is never sent to an image model. Edit them in a channel's **Brand** tab (all three levels,
the channel's videos included) or in the Packaging tab's inspector (this video's chain).

**Brand assets migration (Phase 0).** Older studios kept brand asset bytes in SQLite (`profile_assets`). On first
open the database is backed up to `.studio/profile-assets-migration-backups/<id>/studio.sqlite`, each blob is
written to the file store and verified, recorded as a resource at `profile:<id>` with the same id (brand versions
keep naming it), and only then are the blob rows removed in one transaction. Recorded in `file_store_meta`
(`profile-assets-migration`); safe to run again and resumes after a crash without a second backup. Until then
unmoved assets are read from SQLite. An older app opening a migrated studio cannot read the moved assets (restore
the backup deliberately to downgrade). Storage's unused-files report counts resources and Packaging images as used.

## Profiles, presets and reusing formats

Video formats lists all saved formats grouped by profile, including formats with
no style guide yet. The last selection is remembered in this browser, and the
page URL identifies the selected profile, format and study. Returning to the page
does not hide another profile's formats. Only selection IDs are browser preferences;
format content remains in SQLite.

A profile is a channel, brand or series. A format is a repeatable video style
with its own approved guide and learning history. For example, one channel can
have long-form explainers and Shorts, while a second channel has its own formats.
**Video setup** selects one of the existing workflow presets (on-camera long-form,
voiceover long-form, Short/Reel or product explainer). **Your format name** is a
custom label; several formats can use the same preset and learn different styles.

**Copy an approved format into …** (under More options) starts a new
format in the selected profile from a
reviewed approved version. It copies rules, workflow, reusable assets and personal
skill selections, and records the source profile/format/version. It does not copy
profile brand settings or draft sessions. Evidence remains linked to the retained
original study. Check the guide and assets for channel-specific text or logos.
The new format begins at version 1 and learns independently; changing either copy
does not change the other or existing pinned projects. Stale source-version reviews
are rejected. This is an independent copy, not a live-linked shared format.

Personal skills are studio-wide and can be selected by formats across profiles
through **Choose skills** on the format's Skills tile. Learned packages keep their exact-version applicability;
copy a format to reuse its complete approved package. Source media stay in place.

## Brand profiles, instructions and New video

Since **Flat 3** (24 Oct 2026) the UI has one level of styles: a **style** is a format (one kind of video, e.g.
"Faceless reel") and a **brand kit** is a profile (brand, research, assets, people & places and memories at
`profile:<id>`), shared by every style that uses it (`format.profileId`). Nothing is migrated: existing profiles are
kits, existing formats are styles. The rail links to **My styles** (`#/styles`): a brand kits bar, one flat card per
style (cover, Short/Long badge, kit chip, description, skill version, videos, changes to
review; most recently used first; archived behind Show archived), **New style**, and the shared **Studio
instructions** (`#/styles/instructions`) and **Memories for everything** (`#/styles/memories`).

**Kit colours** (0.1.0-beta.20, `web/kit-colors.js`): every kit shows a colour, its approved brand's first colour,
else the kit colour saved on the profile row (`color`, `#rrggbb`). A new kit gets the first colour of a 12-colour
palette that no other kit shows (cycling by kit count when all are taken); kits made before this version get one
once, when a store opens (`LearningStore.backfillKitColors`: creation order, kits without brand colours first, no
revision change, nothing written when every kit has one). The creator changes it on the kit's Brand tab (**Kit
colour**: the palette or any colour), `POST /api/learning/profiles/<id>/color { expected, color }` (validated,
revisioned, refused for No brand; no format skill rebuild). It is display only: never part of a brand version,
BRAND.md or a project's pinned context. No brand styles take a palette colour derived from the style id.
**Covers**: a card shows a picture only when the studio already has one (`GET /api/learning/formats/<id>/cover?
projects=<newest video ids>`, `server/style-covers.mjs`, 204 when none): the main Packaging thumbnail of one of the
style's videos, else a frame of such a video (the home screen's cached poster frame), else a key frame of an example
the style studied (a saved version's, then a conversation's extracted frames). Otherwise the cover is drawn in the
kit colour: a soft tone, the style's initial, and a 16:9 or 9:16 frame with a presenter (on-camera setups) or a
waveform and captions (faceless). Nothing new is stored for covers. A style's page
(`#/style/<formatId>/skill|examples|brand|people|memories`) has one tab row; the Skill tab's side column opens Files,
Insights, History and Videos as panels (`?panel=files|insights|history|videos`) and **Talk to this style** opens the
format conversation. Brand kits are listed at `#/styles/kits` and each has `#/styles/kit/<profileId>/brand|people|
memories|styles`. Styles without a brand live under one hidden built-in profile (`system: 'unbranded'`, "No brand"),
made the first time a style needs it; it is never listed as a kit and can't be renamed, archived, branded or
researched, and it has no memory or resource rung. **Change kit** calls `POST /api/learning/formats/<id>/move
{ profileId|null, expected }`: the format row moves (drafts, conversations, versions, files and skill selection go
with it), its conversations' memory bindings follow it to the new kit, idle conversation agents restart, and the
format skill is rebuilt; videos made before keep the kit, brand version and memories they pinned (a pin whose format
later moved stays valid). It is refused while a study, reply or frame extraction of that style is running. A kit that
non-archived styles use can't be archived from the app until they move. Beta.14's profile-keyed addresses
(`#/style/<profileId>/formats?format=<F>&tab=…`, `…/brand`, `…/memories`) and every older address (`#/channels…`,
`#/channel/<id>/<tab>`, `#/learning`, `#/memories`, `#/settings/brand`, `#/settings/instructions`, `#/storage`,
`#/dashboard`) redirect through `legacyRoute(hash, lookup)` in `web/nav.js`, which tells profile ids from format ids
with the `/api/learning` view. Code, the API and the SQLite tables keep the `profile` and `format` names.
Settings has six groups (`#/settings/general|agent|recording|editing|export|storage`);
the old one-section addresses (`#/settings/claude`, `#/settings/usage`…) land on their group, at the section.
Storage & backups and Usage are sections of Settings › Storage.

The brand kit's **Brand** tab (also shown on each style using it) owns identity, audience, voice, colours, fonts,
guidance and uploaded brand assets. A kit can be used by several styles. Each style can switch additional enabled
personal skills on or off in its Skill tab's **Uses these skills**; enabled compatible core skills are included
automatically. The approved learned package is selected
separately and supplies its rules, workflow and reusable assets.

Setup and the channel's Brand tab share the same optional profile onboarding. Enter a brand manually
or give a public website to a dedicated research session using the configured agent.
Review the proposed fields and source observations, edit them, then approve. Approval
writes a new immutable brand version only to that profile. Missing browsing tools must
be reported, not replaced with invented evidence. This uses normal agent permissions,
not an OS or network sandbox. Website quality and real-provider behaviour need live
validation; automated tests use a fake agent and synthetic observations.

**Instructions** edits and versions shared `CLAUDE.md`, `AGENTS.md`, `PROMPT.md`,
`INSTRUCTIONS.md`, existing `memory/*.md` and `preferences/skills.json` in SQLite.
First migration imports these known files once and retains the originals. Existing
`BRAND.md`/`STYLE.md` become one “Imported studio” profile, never every profile.
Legacy library assets remain in place: upload the desired images/fonts to the correct
profile explicitly. A missing canonical database cannot be replaced by generated files.
External instruction edits require explicit import; rebuilding preserves displaced
edits under `.studio/instruction-recovery/`. Keep brand-specific prose in its profile.

**New video** (the rail, the Projects page, `N`, a style's or format's page) makes an **Untitled video** straight
away and opens it. It uses the last-used style and format (settings `lastNewVideo`), the style or format it was
started from, or no style. An empty video shows a start screen: **Record now**, **Drop footage** or **Idea &
thumbnail first** (the Packaging stage). The editor's **style picker** (top bar) is a flat list of styles (frame
glyph, name, kit chip; no grouping by kit), then **No style · decide as I go** and **+ New style from this video**. Changing it calls
`POST /api/project-context/<id>/select { profileId, formatId, confirm }`, which re-pins brand, instructions, skills
and format as New video does and rebuilds the context files; a format of another video setup also changes the video's
setup. After a Build step has run it needs `confirm: true` ("Videos keep the style they were built with") and must keep
the same video setup. Formats without a reviewed guide are **basic setup** and can be used immediately.

**Automatic names.** An Untitled video's name is automatic (`nameSource: 'auto'` in project.json) until the creator
renames it. While it is, the project agent is asked to propose a short title (at most 60 characters) once the creator
has described the video, in a fenced ` ```octopus-name ` block that the server applies; saving a Packaging working title
also renames it (and then the agent's later proposals don't replace it). A rename by hand sets `nameSource: 'manual'`
and nothing automatic changes the name again. Only the display name changes, never the folder or id.
Only approved guides are included; draft studies never become project instructions.
A project created without a brand or guide stays that way when either is added later.
You can also create a video without a profile or saved format. It previews the selection, validates compatible enabled skills,
and pins exact brand, instruction, skill and learned versions. Generated files under
`<project>/.octopus/context/` give the agent its selected context, including the pinned
format skill copy in `.octopus/context/.claude/skills/`. Brand palettes are
available to the editor; instructions/format guidance inform the agent's planning.
This does not automatically render or redesign a video. Explicit project choices
still win. **Video defaults** retains background and framing controls; brand colours
and font guidance now live in each style's Brand tab.

Later profile edits apply to new videos, preserving existing project pins. My styles →
Studio instructions says so and counts the videos on an earlier instruction version. A
deliberate learned-format upgrade retains the project's brand and instructions while
selecting the upgraded format and its current skills. Upgrades stay within the video's
channel (another channel's format is refused before anything is written); a video
without a channel joins the format's channel and takes its current approved brand, and
its chat's memory binding gains that channel's and format's memories. The review dialog
lists those changes, and the project's WORKLOG records them. The learning pin, context
pin and memory binding commit in one transaction, only after the context files were
rebuilt; on failure the database, `project.json` and the old files stay as they were.
Generated context edits stop use until restored explicitly; displaced files are
retained. A project whose saved setup can't be used (for example one an older version
upgraded across channels) shows **Repair project setup** in its panel: it keeps what is
still valid, re-pins the rest (the channel's current brand, the current instructions
if the pinned ones are missing) and rebuilds the files. Old projects without a context
pin remain legacy projects; no bulk migration or inferred profile assignment occurs.

Archiving a project stops its chat and keeps its chat log, saved session and database
rows under its id, so restoring it brings it back as it was. A project id is never given
to a new project while any of those (or an archived folder) still exist: a new video
with the same name gets the next free id (`my-video-2`) and starts clean.

**What each chat sees.** Project chats with a pinned setup, and scheduled runs on such a
project, run in the project folder with its pinned instructions, brand and skill copy on
every agent (Claude Code `--add-dir`, Codex's extra skill root, pi `--skill`); the
context names the real working directory and the studio folder. Format conversations
see their channel's format skills and brand research none, through a scoped copy of the
studio skills in `.studio/scoped-skills/<key>/.claude/skills` (reused while the
publications are unchanged; unused copies are removed after a day). For Claude Code these
chats also pass `claudeMdExcludes` (the studio's `CLAUDE.md`, `CLAUDE.local.md`,
`AGENTS.md`) and `skillOverrides` `"off"` for the other format skills with `--settings`,
because Claude Code loads `CLAUDE.md` and `.claude/skills` from parent folders. A
project's pinned copy is named `format-<8 characters>-v<N>` (its pinned version), never the
studio skill's name, so pinned project chats and runs switch off every studio format skill
with `skillOverrides` and load only their own copy (checked with a real Claude Code run,
23 October 2026). A project pinned before this naming gets its copy regenerated under the
new name on its next chat or context load; the old folder, edits included, is moved to
`<project>/.octopus/replaced-format-skills/<time>-format-…`. The skill inventory brief of a
format conversation or brand research names only the format skills that chat can load.
When a draft changes or removes rules but keeps the saved workflow, review warns if the
workflow still uses the old rules' key words (approval is not blocked). With channel profiles, no chat
gets the install-wide brand colours and fonts, the Setup interview's brand line or the
studio `BRAND.md`. In Auto, pi's file changes without a card are limited to the
project's folder (and the temporary folder) for a project chat, like Claude Code's
outside-project check. Switching Codex's provider or pi's model source starts a new
session; a Codex or pi start failure is returned as an error, as for Claude Code.

## Backups and recovery

Storage provides a consistent SQLite backup (`VACUUM INTO`) plus approved package
projections. The database includes approved skills, guides, brand assets, brand/instruction histories,
skill file records and project context pins. Skill file bytes are not in it, so database
backups stay small.
It does **not** back up large media, draft intake or the skill file store: copy those separately for
machine-loss recovery. A backup is stored under `.studio/learning-backups/<id>/`.

**Back up skill files** (Storage) copies the file store to a folder you choose, such as an
external drive, into `<folder>/Video Octopus skill files/` with the same hash layout. It clones
where the disk allows and is incremental: files already there with the right size are skipped.
To restore, copy those folders back into `<studio>/.studio/files/`.

Full restore verifies integrity and a review token, blocks while work is active,
keeps the displaced database, and rebuilds agent skill files. It refuses a backup
that lacks versions or context records pinned by current projects, or predates
canonical profile/instruction storage after migration. It checks every skill file the backup's
versions use: files missing from the file store (and not still in an older backup's SQLite) are
listed in the review and the result, not fatal; restore them from a skill file backup. It does not roll back media or editor
files. Format history can instead change the active version for future projects;
skill history can restore a prior skill snapshot. Neither rolls back application code.

Approved package files can be regenerated from SQLite; externally edited copies are
retained separately. Skills saved through the editor are versioned in SQLite.
Raw database edits are unsupported. Back up before moving storage, and move the
whole studio, not just the generated skill folders.
